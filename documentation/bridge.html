Test Execution Bridge

The Test Execution Bridge is what turns GAIA's test-execution review gates from self-attested into evidence-backed. When the bridge is enabled, a review gate that claims tests passed must be backed by a small execution-evidence JSON file describing the actual run. The review gate inspects that file and refuses to record a passing verdict if the evidence shows a red or skipped suite.

This page explains how to enable the bridge and documents the exact execution-evidence shape the gate consumes — so the evidence you supply actually satisfies the gate. For the companion input manifest that tells the bridge how to run your tests, see the test-environment.yaml Reference; this page covers the evidence the run produces, not the manifest it consumes.

Overview

A test-execution review gate (for example QA Tests, Test Automation, or Test Review) can be recorded as PASSED, FAILED, or UNVERIFIED. With the bridge enabled, a PASSED verdict on one of these gates is only accepted when it is accompanied by an execution-evidence file whose contents confirm a clean run. The gate inspects several per-suite fields in that file and refuses PASSED if any of them indicate a problem.

This closes a gate-integrity hole: without the content check, a gate could be marked PASSED against evidence that recorded a failing suite, and a story with a red test run could reach done with every review gate showing “PASSED”.

Bridge on vs. bridge off

The bridge is controlled by a single boolean in project configuration: test_execution_bridge.bridge_enabled.

StateBehaviour
bridge_enabled: false (default) Test-execution gates are recorded from a written report. No execution-evidence file is required. Suitable for projects that have not yet wired a real test runner.
bridge_enabled: true A PASSED verdict on a test-execution gate requires an execution-evidence file with at least one required suite, and that file's contents are inspected. Evidence showing a non-zero exit code, missing exit codes, any failed tests, a skipped run, or no evaluated required suite causes the gate to refuse PASSED.

Enabling real test execution

Turn the bridge on with the dedicated command: 

/gaia-bridge-enable

This sets test_execution_bridge.bridge_enabled = true in .gaia/config/project-config.yaml. The flag takes effect immediately. The command is idempotent — running it when the bridge is already enabled is a no-op. To turn the bridge back off, use /gaia-bridge-disable.

You also need a manifest

Enabling the bridge tells GAIA to require evidence. To tell GAIA how to run your tests — the runner commands, tiers, and tier-to-gate mapping — author a test-environment.yaml manifest. See the test-environment.yaml Reference.

The execution-evidence contract

When the bridge is enabled, a PASSED test-execution gate is recorded with a path to an execution-evidence JSON file. The evidence is a JSON object with a suites array. Each entry in the array must be an object describing one test tier. The gate reads the following fields:

FieldTypeMeaning
suites[] array of objects One entry per test tier. Every entry must be a JSON object (strings, numbers, and nulls are rejected). Must be a JSON array when present; a non-array value is refused.
suites[].name string Human-readable tier name (used in diagnostics).
suites[].required boolean Whether this tier is required for a passing verdict. true (default when absent) means the gate evaluates this suite; false means the tier is optional and its results do not block PASSED.
suites[].exit_code integer The process exit code for this tier. 0 means the tier passed. Any non-zero value (positive or negative, including signal-killed processes) is treated as a failure. Required on every required suite — a required suite that omits exit_code is refused (missing evidence is not the same as passing evidence).
suites[].fail_count integer Number of failed tests in this tier. The gate sums fail_count across required suites. A missing count is treated as 0.
suites[].timeout boolean Whether the tier was killed by a timeout. true on a required suite yields a BLOCKED verdict in the verdict resolver.
suites[].skip_reason string (optional) Present on placeholder suites that were not actually exercised (e.g. “no command declared”). A suite with skip_reason does not count as an evaluated required suite.
skipped boolean Top-level flag: whether the entire run was skipped. A real run stamps false; only strict boolean true means “not run” (values like 0 or "" are not treated as skipped).

A clean run that the gate will accept as PASSED looks like this (at least one required suite with exit_code: 0): 

{
  "skipped": false,
  "suites": [
    { "name": "unit",        "required": true,  "exit_code": 0, "fail_count": 0, "timeout": false },
    { "name": "integration", "required": true,  "exit_code": 0, "fail_count": 0, "timeout": false },
    { "name": "visual",      "required": false, "exit_code": 1, "fail_count": 3, "timeout": false }
  ]
}

In the example above, the optional “visual” tier failed but did not block PASSED because it is marked required: false. The two required tiers both have exit_code: 0.

Additional fields (timestamps, durations, command strings, per-suite pass counts) are ignored by the gate and safe to add for your own auditing.

When the gate refuses PASSED

The gate refuses to record PASSED — and tells you why — when the evidence shows any of the following. The checks run in the order shown; the first match fires.

ConditionGate response
--plan-id passed on a test-execution gate (QA Tests, Test Automation, Test Review), including a sprint-scoped auto-generated plan identifier Refused with a diagnostic. Test-execution gates require real execution evidence; use a plan-only gate (e.g. test-automate-plan) for plan approvals. This refusal applies even when the proof-of-execution off-switch is set.
--report-missing-reason with PASSED on a test-execution gate The verdict is coerced to UNVERIFIED and the reason text is written into the Report column. This coercion applies even when the proof-of-execution off-switch is set.
.suites present but not a JSON array Refused (malformed evidence shape).
Any entry in suites is not a JSON object (e.g. a string, number, or null) Refused (non-object entry). Fix the evidence file.
No required suite evaluated (all suites are optional, the suites array is empty, or the suites key is missing; placeholder suites with skip_reason do not count as evaluated) Refused. A project with no configured required test tier cannot record a test-execution gate as PASSED. The remedy is to configure at least one required tier in your test environment, or record plan approvals on a plan-only gate.
A required suite is missing the exit_code key Refused (the diagnostic names each suite without the key). Missing evidence is not the same as passing evidence.
Any required suite has a non-zero exit_code (positive or negative, including signal-killed processes) Refused (red suite). Fix the failing tests and re-capture evidence, or record FAILED.
Summed fail_count across required suites is greater than 0 Refused (failing tests). Fix and re-capture, or record FAILED.
skipped is strictly true Refused (run was not exercised). Run the suite and re-capture, or record UNVERIFIED.

A FAILED verdict is always allowed against red evidence — recording that a gate failed is correct and expected. The refusal applies only to a PASSED claim that the evidence contradicts.

Documented escape hatches

Two deliberate bypasses exist for situations where attaching real evidence is not possible. Recording a gate with an explicit missing-evidence reason satisfies the gate without an evidence file (the reason is preserved for audit), and a project can disable the content check entirely via the REVIEW_GATE_PROOF_OF_EXECUTION=off environment override. Both are escape hatches — the default, enabled behaviour is the evidence-backed path above. Note that the --plan-id refusal and the --report-missing-reason coercion still apply when the off-switch is set.

Worked example

Suppose a suite ran but two integration tests failed. The execution-evidence file would record: 

{
  "skipped": false,
  "suites": [
    { "name": "unit",        "required": true,  "exit_code": 0, "fail_count": 0, "timeout": false },
    { "name": "integration", "required": true,  "exit_code": 1, "fail_count": 2, "timeout": false }
  ]
}

Attempting to record this gate as PASSED is refused on two counts: the integration suite has a non-zero exit_code and the summed fail_count across required suites is 2. The correct action is to fix the two failing integration tests, re-run, and re-capture evidence showing exit_code: 0 with all fail_count values at 0 — or to record the gate as FAILED until the fix lands.

Placeholder suites

When a tier is configured but has no runner command, the bridge emits a placeholder suite with a skip_reason: 

{
  "skipped": false,
  "suites": [
    { "name": "e2e", "required": true, "exit_code": 0, "fail_count": 0, "timeout": false, "skip_reason": "no command declared" }
  ]
}

A placeholder does not count as an evaluated required suite. If every required suite is a placeholder (or if the suites array is empty), the gate refuses PASSED with “no required suite evaluated.”
