/gaia-design-review

user-facing
Category:
Reviews
Lifecycle phase:
3 -- Solutioning
Arguments:
none

What it does

/gaia-design-review reads the design project back through the Claude Design integration, reviews screens and components against the UX design document and accessibility rules, and drives an iterative stakeholder approval loop. Findings are severity-tagged. Verdicts are recorded through the sole design-record writer. When a stakeholder comment implies a requirement change, the loop halts and routes through the feature intake workflow.

When to use it

  • After a design project has been created and published via /gaia-create-ux.
  • When stakeholder review and approval of the design is needed.
  • To reconcile designer-side changes back into the derived UX design document.

Prerequisites

  • UI-present gate. compliance.ui_present must be true in project config.
  • Design record. A design record must exist at .gaia/state/design-record.yaml.
  • UX design document. The UX design must exist at .gaia/artifacts/planning-artifacts/ux-design.md.

How to invoke

/gaia-design-review

What it does step by step

  1. Read-back Reads the design project through the Claude Design integration as the authoritative source, wrapping content in data boundary markers.
  2. Findings Compares project content against the UX design document and accessibility rules. Emits severity-tagged findings (high, medium, low, info). Missing required components are findings in this same pass.
  3. Internal review Records an internal verdict before any stakeholder sees the findings. High-severity findings block stakeholder delivery unless the user explicitly accepts them.
  4. Stakeholder delivery Re-reads the project for current state. Presents findings to each stakeholder. Records their verdict (approved, changes-requested, or escalated) through the sole writer.
  5. Convergence and transition Checks convergence before transition. On full approval: transitions to approved. On changes requested: bumps iteration. On escalation: halts and routes to feature intake.
  6. Delta sync Reconciles designer-side changes from the project into the derived UX design document.
  7. Iteration loop Returns to Step 1 for each new iteration until the design is approved or escalated.

Example session

> /gaia-design-review

Reading design project via Claude Design integration...
Project content loaded (3 screens, 12 components).

Findings (4 total):
  [high] Missing UX-required component: navigation-drawer
  [medium] Spacing inconsistency on the settings screen
  [low] Button border radius differs from design system token
  [info] Consider adding hover states to card components

Internal review: changes-requested (1 high-severity finding)
High-severity findings block stakeholder delivery.
Accept findings and proceed? [y/n]

What to run next

  • /gaia-create-ux — create or update the UX design document.
  • /gaia-validate-design-a11y — run an accessibility audit against the design.
  • /gaia-add-feature — process an escalated requirement change.

Troubleshooting

Skill skips with "compliance.ui_present is not true"
Set compliance.ui_present: true in project config via /gaia-config-compliance.
No design record found
Create a design project first with /gaia-create-ux, which initializes the design record.
Convergence reports "vacuous"
No stakeholders are tagged with design or ux tags. Add stakeholder files to .gaia/custom/stakeholders/ with the appropriate tags.

Related commands

  • /gaia-create-ux — creates the UX design and initializes the design record.
  • /gaia-validate-design-a11y — accessibility validation for the design.
  • /gaia-review-all — runs all review workflows including this one.
