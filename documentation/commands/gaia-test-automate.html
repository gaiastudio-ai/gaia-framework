/gaia-test-automate

user-facing
Category:
Testing
Lifecycle phase:
4 -- Implementation
Arguments:
[story-key] [--status|--add-scenario|--scaffold]

What it does

/gaia-test-automate expands automated test coverage for a story. In its default mode, it plans which tests to write based on acceptance criteria coverage gaps, then implements the tests using the appropriate stack developer agent. It also supports three sub-commands: --status (show coverage map), --add-scenario (add a custom test scenario), and --scaffold (generate placeholder test skeletons).

When to use it

  • A story's QA review surfaced uncovered acceptance criteria and you want to fill the gaps.
  • You want to check the current test coverage status for a story (--status).
  • You need to add a custom edge-case test scenario not covered by the standard AC-to-test mapping (--add-scenario).
  • You want placeholder test skeletons generated so a developer can fill in the assertions later (--scaffold).

Prerequisites

  • A story file must exist under .gaia/artifacts/implementation-artifacts/.
  • For default mode, the story should be in review status with implementation complete.

How to invoke

/gaia-test-automate E3-S7
/gaia-test-automate E3-S7 --status
/gaia-test-automate E3-S7 --add-scenario
/gaia-test-automate E3-S7 --scaffold

The story key is always required. The sub-command flags select which operation to perform.

What it does step by step

Default mode (fill gaps)

  1. Analyze coverage Maps each acceptance criterion to existing test files and identifies gaps.
  2. Plan tests Proposes which tests to write for uncovered ACs, including test type (unit, integration, e2e).
  3. Implement tests Delegates test writing to the appropriate stack developer agent.
  4. Verify Runs the new tests to confirm they pass. Updates the Review Gate Test Automation row.

--status sub-command

Displays a coverage map showing each AC, its mapped test case, test type, and file path. Summarizes as "N/M generated (X%)".

--add-scenario sub-command

Allocates the next custom scenario ID (CS-NNN), writes the scenario to the story's custom scenarios table and the project index.

--scaffold sub-command

Generates placeholder test skeletons for uncovered ACs. Does not update the Review Gate to PASSED -- scaffolds are incomplete by definition.

--mutation sub-command

Runs the mutation runner for a story to produce mutation evidence. This is the sole producer of mutation evidence; review consumers (QA, test-review) read the score but never invoke the runner. The run is wrapped in the heavy-reviewer slot semaphore. Evidence is written next to the story's execution evidence. When test_execution.mutation_thresholds is absent from the project config, this sub-command exits immediately with no side effects.

When it runs. With thresholds configured, the same run also starts automatically after a green execution. It first checks the covering tests pass on unmutated code; if they do not, it refuses to score. A run that cannot produce a usable gate records blocking_failure: runner_unavailable and the verdict is BLOCKED. Run it before a review round: without evidence for the current commit, QA and test review report the check as errored on P0 and P1 stories.

Time limit. Each test run under one interpreter has a limit of 30 seconds by default. Raise it with --timeout <seconds> on subcmd-mutation.sh or the GAIA_MUTATION_TIMEOUT environment variable, which also reaches the automatic run. Covering tests that run out of time on unmutated code are reported as a timeout, not as failing tests.

No mutants. A P2 or P3 story gets gate advisory with no score. A P0 or P1 story gets gate not_applicable with a zero_mutant_reason only when a non-empty File List has no entry any adapter covers, for example a docs-only, tests-only or Python-only story; QA and test review report that as skipped. An empty or unreadable File List, a covered file missing from the worktree, or a covered file with no mutants gets gate errored. A File List line that names no path, or an adapter manifest that is missing, malformed or has no usable file-extensions, counts as unreadable: nothing runs. A file is a test only if it is a .bats file or sits under a tests or test directory; scripts/test_calc.sh is a source.

Reading the File List. The runner reads a path from a line however it is written: backticked, bold, quoted, as a link target, in a table cell, comma-separated, with a label in front or a note or :12 behind. Every path on a line counts, so a source named in a note counts too. Paths inside a fenced block are read. The following structural forms are ignored: headings, blank lines, table headers and separators, HTML comments, fence markers (```), lines with no letter or digit, any line whose text ends with a colon (plain Modified:, bold **Modified:**, **Modified**:, or a list item - Modified:), and bold title lines such as **Modified files**. Indented or quoted prose, and any other line that names no path, inside or outside a fence, is unreadable and gives errored.

What is stored. The stored test_output holds test result lines only: ok or not ok, the number and the test name, scrubbed and capped at the newest 4 KB of whole lines. Nothing else a test prints is stored, and a command that prints no result lines stores nothing. A secret written into a test name is removed only if scrubbing recognises it. If scrubbing fails, a fixed message is stored instead. Adapter and generator stderr goes to the terminal, not the evidence.

Thresholds configuration. Add test_execution.mutation_thresholds to your project config with per-priority integer thresholds (0-100). Missing priorities default at the point of use (P0: 80, P1: 60, P2: 0, P3: 0). When the key is absent, mutation testing is off and no behaviour changes on upgrade.

Outputs

OutputLocationDescription

Findings are recorded in a shared per-story findings register. The verdict rule uses the register: a gate is failed only when an unresolved blocker exists. The shared rubric defines severity levels, the blocker definition, and the verdict rule.

Example session

> /gaia-test-automate E3-S7 --status

  AC2   TC-002   integration   tests/int/auth.spec.ts
  AC3   --       --            (not yet automated)

Summary: 2/3 generated (67%) | 1 pending automation

> /gaia-test-automate E3-S7

Planning tests for 1 uncovered AC...
  AC3: password-reset edge case -> unit test

Implementing tests...
  Written: tests/unit/password-reset.test.ts

Running tests... 1 passed.
Review Gate updated: Test Automation -> PASSED

What to run next

  • /gaia-review-all -- run remaining reviews to complete the Review Gate.
  • /gaia-test-gap-analysis -- verify overall coverage after automation.

Troubleshooting

"Story must be in review status"

Default mode requires the story to be implemented first. Use --scaffold to generate skeletons before implementation.

Tests fail after generation

The generated tests may need manual adjustment. Fix the assertions and re-run.
